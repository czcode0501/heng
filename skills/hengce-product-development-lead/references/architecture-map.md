# 衡策核心架构地图

## 推荐边界

1. 数据源适配层：访问 BaoStock、yfinance、SEC、新闻或券商只读接口，保留供应商原始状态。
2. 标准化事实层：统一代码、时间、单位、来源、质量、缓存和冲突表达。
3. 领域计算层：市场择时、板块轮动、资金流、技术指标和公司研究等可测试计算。
4. 方法论决策层：经理契约、证据闸门、反方挑战、仓位边界与复核纪律。
5. 应用/API 层：编排用例、缓存和错误映射，向浏览器提供稳定合同。
6. 界面层：围绕用户行动展示结论、证据、等待条件、失效位和数据状态。
7. 运行保障层：健康检查、日志、监控、凭证处理、测试、构建和发布说明。

依赖应从上层指向下层稳定合同，供应商对象不能穿透到页面，页面文案也不能反向成为领域计算规则。

## 当前阶段建议

项目目前适合保持本地模块化单体：JavaScript/Vite 界面、本地 API、Python 数据与计算模块。现阶段优先建立清晰模块合同、数据质量类型、架构决策记录和端到端验收，不为“看起来专业”提前引入微服务、消息队列或复杂状态框架。

当同一模块出现独立部署需求、明显不同的扩展瓶颈、权限隔离要求或团队所有权边界，并且拆分收益可用观测数据证明时，再评估服务化。

## 架构评审问题

- 原始事实是否只有一个规范来源，还是被多个页面重复计算？
- 缺失、过期、缓存、冲突和失败能否从源头一路传到用户？
- 外部供应商失效时，系统是明确降级还是悄悄给出看似正常的数字？
- 核心算法是否能在无网络环境用固定样本复现？
- 方法切换是否只改变权重、门槛和纪律，而没有改写事实？
- API 变化是否兼容现有页面和测试？
- 新手能否看到行动、区间、数量、等待条件与失效位？
- 这项复杂度是否解决已经发生的问题，还是只服务于假想规模？
